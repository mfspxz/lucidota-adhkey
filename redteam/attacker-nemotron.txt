### Looking at evidence.rs:

```rust
pub fn evaluate_claim(claim: &HumanClaim, now: u64) -> EpistemicState {
    // Revocation is sticky and checked first.
    if claim.evidence.iter().any(|e| e.revoked) {
        return EpistemicState::Revoked;
    }
    if let Some(exp) = claim.expires_at {
        if now >= exp {
            return EpistemicState::Expired;
        }
    }
    if claim.evidence.is_empty() {
        return EpistemicState::Claimed;
    }
    // Expired evidence does not count toward support.
    let live: Vec<&Evidence> = claim
        .evidence
        .iter()
        .filter(|e| e.expires_at.map(|x| now < x).unwrap_or(true))
        .collect();
    if live.is_empty() {
        return EpistemicState::Claimed;
    }
    // Policy evaluation: the policy names a minimum evidence bar.
    // The core does not know what "medium" means — the policy does.
    // Here: SUPPORTED unless the policy's bar is met AND no conflict.
    // Conflict detection: two live evidence items from different witnesses
    // disagreeing is out of scope for the core; witnesses report conflict
    // via revocation. A policy hook can upgrade this.
    let _ = &live;
    EpistemicState::Supported
}
```

**BUG: No conflict detection despite Conflict state existing** - C4 in AUDIT.md covers this ("Conflict is dead"). But also: the comment says "witnesses report conflict via revocation" - but revocation is per-evidence, not per-claim. Two pieces of evidence from different witnesses could contradict each other without either being revoked.

**BUG: Evidence digest never verified** - G5 in AUDIT.md covers this.

**BUG: `establish` function takes `policy_satisfied: bool`** - C3 in AUDIT.md covers this.

```rust
pub fn authorize_with_freshness(
    state: EpistemicState,
    freshness: Option<&Freshness>,
    max_staleness_secs: u64,
    now: u64,
) -> AuthorizationVerdict {
    if !state.authorizable() {
        return AuthorizationVerdict::CannotEstablish(format!(
            "epistemic state {:?} is not authorizable",
            state
        ));
    }
    match freshness {
        None => AuthorizationVerdict::CannotEstablish(
            "no freshness witness; cannot establish current authority".into(),
        ),
        Some(f) => {
            if now.saturating_sub(f.known_at) <= max_staleness_secs {
                AuthorizationVerdict::Authorized
            } else {
                AuthorizationVerdict::AuthorizedAsOf(f.known_at)
            }
        }
    }
}
```

**BUG: Freshness witness not verified** - G3 in AUDIT.md covers this. But also: `f.state_version` is never checked against anything. The version is accepted but not validated.

**BUG: `max_staleness_secs` used with `saturating_sub`** - If `now < f.known_at` (clock skew), `saturating_sub` returns 0, which is <= max_staleness_secs, so it returns `Authorized`. A future-dated freshness attestation would be treated as fresh. This is a clock skew vulnerability.

### Additional issues I'm finding:

1. **Recovery policy validation doesn't check for duplicate key IDs** - `RecoveryPolicy::valid()` doesn't check uniqueness of `recovery_key_ids`. If policy has `[REC-1, REC-1, REC-2]` with threshold=2, the `BTreeSet` in `recover()` would count only 1 distinct key, but the policy says 3 keys. This is a configuration footgun.

2. **No validation that recovery keys are distinct from active keys** - A key could be both an authentication key and a recovery key. The protocol doesn't forbid this, but it might be a security issue (key compromise affects both).

3. **`KeyRecord.seq` is per-key but `Event.seq` is global** - The `KeyRecord.seq` is set at activation and never updated. The `Event.seq` is global history sequence. This inconsistency could cause confusion.

4. **`Identity.identifier` and `Identity.subject` are both Strings** - No validation they match or are well-formed. Critique #1, #5 cover this partially.

5. **`VerificationMethod.public_key_multibase` is String** - No validation it's valid multibase. Could be garbage.

6. **`Capability.nonce` is String** - No length limit, could be huge (DoS via memory in seen_nonces).

7. **`RecoveryCompleted` event stores `approvals: usize`** - Critique #10 covers this ("approvals: usize destroys provenance").

8. **No replay protection for recovery operations** - The recovery function doesn't take a nonce or check for duplicate recovery attempts. An attacker could replay a recovery approval set.

9. **`transition_key` for Lost→Active ("found again") requires no proof** - C6 covers this.

10. **`KeyState::Expired` has no transitions** - Once expired, key is stuck. Is this intentional? The transition table doesn't allow Expired→anything. But `can_transition_to` doesn't have Expired as source. So Expired is terminal like Revoked. But no test covers this.

11. **`verify_capability` checks `ctx.now >= cap.issued_at`** - But `issued_at` could be in the future (clock skew). If `issued_at > now`, capability is "not yet valid" and fails. But if `issued_at` is far in future, it fails. This is correct behavior but worth noting.

12. **`Capability` has no signature field** - The signature is verified externally via `VerifierContext.signature_valid`. The capability itself doesn't carry the signature. This is by design (separation) but means the capability struct isn't self-contained.

13. **`Receipt` has no timestamp** - When was the verification performed? Not recorded.

14. **`Receipt` has no verifier identity** - Who performed the verification? Not recorded.

15. **`Established` carries `key_state_at_check` but not `checked_at` timestamp** - When was the establishment done?

16. **`HumanClaim.issued_by` is a Witness** - But Witness has no key/signature. It's just an ID string. Critique #8 covers this ("Witness isn't a witness").

17. **`Evidence.witness` is a Witness** - Same issue.

18. **`Freshness.witness` is a Witness** - Same issue, plus G3.

19. **No canonical serialization** - Critique #21, G4.

20. **`Error::InvalidPolicy(String)` is catch-all** - Used for subject mismatch, audience mismatch, empty scope, nonce replay, expiry, bad signature. Different errors conflated.

21. **`recover` function: `new_key: KeyId` taken by value, `old_key: &KeyId` by reference** - Inconsistent API.

22. **`activate_key` called at end of `recover`** - If it fails, recovery event already recorded, old key revoked. State corruption.
